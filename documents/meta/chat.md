핵심 시스템
1. Multi-Layer 3D Factory
공장과 플랫폼을 세 개의 건설 레이어에 걸쳐 설계할 수 있다. 단순히 옆으로 넓히는 게 아니라, 위아래 레이어와 연결해서 공간 효율을 높이는 방식이다. 정확도: 높음. 

2. Space Train
대규모 공장에서 장거리 운송을 담당한다. 1.0 패치에서 기차 처리량도 강화되어, 패키지 크기가 180 → 360 shapes, 유체는 1,800 → 3,600 liters로 증가했다. 정확도: 높음. 

3. Research / Upgrade
목표 도형을 납품하면 새 건물, 메커니즘, 업그레이드가 해금된다. Steam 설명은 연구 시스템이 새 건물, 메커니즘, 업그레이드를 열어 공장 설계 방식을 확장한다고 설명한다. 정확도: 높음. 

4. Blueprint Library
공장 설계를 저장, 불러오기, 내보내기, 공유할 수 있다. 대규모 모듈형 공장을 만들 때 핵심 기능이다. 정확도: 높음. 

5. Make-Anything-Machine, MAM
고급 단계에서는 어떤 목표 도형이 들어와도 자동으로 생산 라인을 재구성하거나 신호 기반으로 처리하는 Make-Anything-Machine 설계가 가능하다. 공식 사이트는 고급 wiring system으로 MAM을 만들 수 있다고 설명한다. 정확도: 높음.

결론
shapez 2는 “전투 없는 Factorio식 도형 자동화 퍼즐”에 가깝다.
핵심 재미는 자원을 캐는 게 아니라, 도형 생산 공정을 어떻게 모듈화하고, 처리량을 늘리고, 대규모 공장으로 확장하느냐에 있다.

현재 1.0 기준으로는 콘텐츠가 크게 확장되었고, 특히 Manufacture Mode + Steam Workshop 모딩 + 83개 업적 + Classic 확장 때문에 Early Access 때보다 완성도가 높아진 상태다. 자동화, 로직 설계, MAM, 대규모 시스템 최적화를 좋아하면 꽤 잘 맞는 게임이다.

결론
너 혼자 쓰는 로컬 shapez 2 퍼즐 Solver라면 Qt, 정확히는 PySide6 추천.
웹으로 공유하거나 브라우저 기반 툴처럼 만들 거면 Django보다는 FastAPI + React/Cytoscape.js 쪽이 더 맞음.

Django는 “solver 앱” 자체에는 약간 무겁다. 데이터베이스, 로그인, 관리자 페이지, 서버 배포가 필요한 웹서비스라면 좋지만, 단순히 도형 입력 → 풀이 탐색 → 그래프 시각화 → 이미지/블루프린트 출력 구조라면 Django의 장점이 크게 살아나지 않는다.

4. 생산량 계산 모델
기본 공식
required_input_rate = target_output_rate × operation_input_ratio / operation_yield
예시:

목표 output = 120 shapes/min
어떤 operation이 input 2개로 output 1개를 만든다면:

필요 input 총량 = 120 × 2 = 240 shapes/min
각 operation마다 다음 metadata가 필요하다.

@dataclass
class MachineSpec:
    operation: str
    input_ports: int
    output_ports: int
    base_rate_per_min: float
    yield_ratio: float
    waste_outputs: int
5. Miner 수 계산
기본 공식
needed_miners = ceil(required_raw_rate / miner_output_rate)
예시:

필요 raw circle = 720 shapes/min
miner 1개 생산량 = 180 shapes/min

needed_miners = ceil(720 / 180) = 4
단, shapez 2는 게임 버전/업그레이드/모드에 따라 rate가 바뀔 수 있으므로 숫자를 코드에 박으면 안 된다.

추천 방식:

# game_data/shapez2_v1_0.yaml

rates:
  miner:
    base_output_per_min: 180
  belt:
    tier_1_per_min: 180
    tier_2_per_min: 360

machines:
  cutter:
    input_count: 1
    output_count: 2
    rate_per_min: 180
  rotator:
    input_count: 1
    output_count: 1
    rate_per_min: 180
  stacker:
    input_count: 2
    output_count: 1
    rate_per_min: 180
정확한 값은 나중에 실제 게임 데이터 기준으로 검증해야 한다. 지금 단계에서는 계산 엔진을 config-driven으로 만드는 것이 더 중요하다.

7. Background Task 구조
Solver는 오래 걸릴 수 있으니 아래 구조가 좋다.

User submits target shape
→ Django creates SolverRun(status="queued")
→ Celery task starts
→ Solver updates progress
→ Frontend polls or receives websocket event
→ Result graph/statistics displayed
Django async view 자체는 존재하지만, 공식 문서상 ASGI에서 전체 async stack일 때 장점이 있고 WSGI에서는 성능 페널티가 있다. CPU-heavy solver를 view에서 직접 오래 돌리는 구조는 피하는 게 맞다. 

추천
작업	기술
짧은 API 요청	Django view / DRF / Django Ninja
긴 solver 실행	Celery worker
progress update	Redis + polling 또는 Channels
실시간 그래프 업데이트	Django Channels / WebSocket
간단한 MVP	1초마다 polling
Channels는 Django를 HTTP 너머 WebSocket 같은 프로토콜까지 확장하는 프로젝트다. 실시간 progress나 solver 상태 업데이트를 넣을 때 적합하다.

좋은 구조
# view
def create_solver_run(request):
    run = SolverRun.objects.create(status="queued")
    solve_shape_task.delay(run.id)
    return redirect("solver_run_detail", run_id=run.id)
# celery task
@shared_task
def solve_shape_task(run_id):
    run = SolverRun.objects.get(id=run_id)
    run.status = "running"
    run.save()

    result = solver_core.solve(...)

    run.result_graph = result.graph
    run.statistics = result.statistics
    run.status = "completed"
    run.save()
