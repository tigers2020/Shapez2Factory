# 모든 개발자가 알아야 할 레이턴시 수치 (Latency Numbers Every Programmer Should Know)

## 개요

컴퓨팅 시스템의 주요 연산 레이턴시를 정량화한 레퍼런스 표. 정확한 수치 외우기가 아닌 **차수(order of magnitude) 감각**을 기르는 것이 핵심 목적.

- **참조 빈도**: DDI (Designing Data-Intensive Applications), Alexis Akhmetli's System Design Interview, ACM SIGMOD, Google Research, Cornell University 학술 자료
- **해결 질문**: 캐시 도입 가치가 있나? 네트워크 hop 감소로 얼마나 빨라질까? 메모리에 두는 게那么大 차이일까? 리전 분리로 응답이 얼마나 느려질까?

---

## 역사: 세 인물, 세 단계

### 1. Peter Norvig (2001) — 로컬 PC 관점

**출처**: 하이퍼글리펁 에세이 부록. 스탠퍼드・구글 출신, AI 교과서 저자.
**취지**: 프로그래머의 알고리즘 작성 시 마주하는 **단일 머신의 물리적 제약** 설명. 10년이 필요하다며 24일/21일 독学法 책 비판.

| 연산 | 레이턴시 |
|------|----------|
| CPU 명령 실행 | ~1 ns |
| L1 캐시 참조 | ~0.5 ns |
| L2 캐시 참조 | ~7 ns |
| 메인 메모리 참조 | ~100 ns |
| 1 Gbps 네트워크, 1 KB 전송 | ~20 μs (2만 ns) |
| 메모리에서 1 MB 순차 읽기 | ~250 μs |
| 디스크 탐색 (seek) | ~8 ms |
| 디스크 읽기 | ~20 ms |
| 미국 → Европа 패킷 왕복 | ~150 ms |

> 핵심: 나노초(ns) vs 마이크로초(μs) vs 밀리초(ms) — 단위가 바뀔 때마다 **3~4개 차수** 차이.

### 2. Jeff Dean (2009) — 분산 시스템 관점

**출처**: LADIS 학회 키노트. MapReduce, BigTable, TensorFlow 공동 설계자.
**추가 항목**: SSD랜덤/순차읽기, 데이터센터 내부 RTT, 압축 비용.
> "중요한 것은 실제로 만들지 않고도 시스템의 성능을 추정할 수 있는 능력이다."

| 연산 | 레이턴시 |备注 |
|------|----------|------|
| 1 KB gzip 압축 | ~3 μs | 네트워크 직전송 10μs vs 압축+전송 3+5=8μs → 압축이 더 빠름 |
| SSD 4KB 랜덤 읽기 | ~50~100 μs | HDD 8ms 대비 ~100배 빠름 |
| SSD 1 MB 순차 읽기 | ~300~500 μs | |
| 데이터센터 내부 RTT | ~500 μs | Jeff Dean 추가, 분산 시스템에서 결정적 계층 |

> **Jonas Bonér (2012)**: GitHub에 정리하면서 SSD 항목 2개 추가. 현재 업계 표준으로 널리 인용됨.

### 3. Colin Scott — 시간의 함수로 시각화

**작업**: 위 수치를 하드웨어 발전 곡선으로 모델링, 연도 슬라이드로 인터랙티브 시각화 (colin-scott.github.io/latency numbers).
- **강점**: ~30년에 걸친 하드웨어 evolution을 한눈에, 절대값보다 **상대적 서열/격차**가 변하지 않음을 직관화.
- **약점**: 메모리/네트워크처럼 개선 속도가 느린 영역은 실제 벤치마크와 괴리 가능.

## 완전한 레이턴시 표 (요약)

| 계층 | 연산 | 레이턴시 (~) | 단위로 기억하기 |
|------|------|------------|----------------|
| **CPU** | 명령 실행 | 1 ns | 나노초 |
| **L1 캐시** | 참조 | 0.5 ns | 나노초 |
| **L2/L3 캐시** | 참조 | 7~20 ns | 나노초 |
| **메모리 (RAM)** | 참조 | 100 ns |백 ns = 백만 분의 1 초 |
| **메모리** | 1 MB 순차 읽기 | 250 μs | 마이크로초 |
| **압축** | 1 KB gzip | 3 μs | 마이크로초 |
| **SSD** | 4KB 랜덤 읽기 | 50~100 μs | 마이크로초 |
| **네트워크 (DC 내부)** | RTT | 500 μs | 마이크로초 |
| **HDD** | seek | 8 ms | 밀리초 |
| **HDD** | 읽기 | 20 ms | 밀리초 |
| **네트워크 (대륙간)** | RTT | 150 ms | 밀리초 |

### 격차 요약

```
CPU → L1 캐시:       ~2x
L1 → 메모리:        ~100~200x
메모리 → SSD:       ~100~200x
SSD → HDD:          ~100x
DC 내부 네트워크 → 대륙간:  ~300x
```

## 실무 의사결정 시나리오

### 1. 캐시 도입

**상황**: HDD 기반 DB 조회가 느려 Redis 캐시 검토.

| 수단 | 레이턴시 | 차수 |
|------|---------|------|
| HDD 디스크 seek | ~10 ms(ms) | 밀리초 |
| DC 내부 RTT (Redis 원격 조회) | ~500 μs(마이크로초) | 마이크로초 |
| Redis 메모리 조회 | ~100 ns(ns) | 나노초 |

→ HDD vs Redis: **~10만 배 차이**. 도입 가치 명확. 하지만 SSD 기반 DB면 격차 축소 → 투자/분산 관점으로 재검토 필요.

---

### 2. 마이크로서비스 분리 비용

**상황**: 특정 기능을 별도マイクロ로 분리하는가?

| 수단 | 레이턴시 | 차수 |
|------|---------|------|
| 로컬 메모리 함수 호출 | ~1 ns | 나노초 |
| DC 내부 RPC/네트워크 호출 | ~500 μs | 마이크로초 |

**격차**: **~50만 배**. 여기에 직렬화/역직렬화 비용 추가 → 실제 100만 배 이상.
→ 호출 빈도가 높은 기능은 분리 신중. 무조건 분리가 답 아님. 확장성/독립성 측면과 트레이드오프.

---

### 3. 시스템 디자인 인터뷰: 초당 100만 QPS URL 단축 서비스

| 근거 | 논리 |
|------|------|
| 메모리 조회 ~100 ns → 초당 이론상 ~천만 건 처리 가능 | 메모리에서 끝나는 작업이면 단일 서버도 충분 |
| 디스크 DB 조회 수 ms → 초당 수백 건이 한계 | 디스크 I/O가 병목이 되므로 캐시 필수 |
| 네트워크 호출 500 μs 이상 | 서비스간 호출 횟수 최소화해야 병목 방지 |
| 결론 | 캐시 필수 + 샤딩 필요 + 호출 횟수 최소화 — 숫자로 정량화 가능 |

## 주의사항 4가지

| # | 주의점 | 내용 |
|---|--------|------|
| 1 | 절대 수치 외우지 마라. 차수 감각이 핵심. | 실제 환경과 완벽 일치하지 않음. ns/μs/ms 단위 차이가 의미가 있음. |
| 2| 다 외울 필요 없음. 핵심만 보유. | L1 캐시, 메모리, SSD, DC RTT, HDD, 대륙간 — 이 정도면 의사결정 충분.|
| 3 | 절대값에 매달리지 마라. 상대적 배수가 지속됨. | 연도마다 값 변하지만 "램이 SSD보다 ~200배 빠름" 같은 비율은 유지.|
|4 | 레이턴시 ≠ 전부. 스루풋 함께 고려. | 병렬/배치/순차 처리로 레이턴시 비용 상쇄 가능. 10개 호출을 한 번으로 묶으면 네트워크 오버head가 10→1로 줄어듦. |

## 핵심 메시지

> **정확한 숫자보다 중요한 것은 차수의 감각.**
> CPU(ns) < 메모리(μs) < 디스크(ms) < 네트워크(ms~초) — 이 서열이 어떤 하드웨어 세대에서도 유지됨.
> 새로운 기술 등장 시 "대략 얼마 정도 비용이 들겠구나"를 추정할 수 있다면 그건 아키텍트의 감각. 코드를 잘 쓰는 게 아니라 **근거 있는 의사결정을 할 수 있는가** 가 코드 작성자와 설계자를 가름.
